## 発端：「人がコードレビューしない」という議論

2025年末から2026年にかけて、X（旧Twitter）上で「人がコードレビューをしなくなる」という議論が盛り上がった。きっかけとなったのは、[@kenn（Kenn Ejima）氏](https://x.com/kenn/status/2058435100380209639)や[@sonicair氏](https://x.com/sonicair/status/2057801166554317161)のポストだ。

AIエージェントがコードを書き、AIがレビューし、人間はマージボタンを押すだけ——そんな未来がすぐそこに来ているのではないか、という問題提起である。

これは単なる未来予測ではない。すでにAnthropicやStripeといった企業では、AIエージェントが開発プロセスの中核を担い始めている。本記事では、これらの先進事例を踏まえながら「人がコードレビューしない」とは実際には何を意味するのかを掘り下げる。

## Anthropicの現実：レビューが追いつかない問題

Anthropicは自社の開発にClaude Codeを全面導入している。その結果、エンジニア1人あたりのコード出力量は**前年比200%**に増加した。マージされるコードのうちAIが書いた割合は平均約50%、一部チームでは90%に達する。

しかし、コードレビューはこの増加に追いつけなかった。**実質的なレビューコメントが付くPRは全体のわずか16%**。つまり、大量のAI生成コードが実質的にノーレビューでマージされていたのだ。

この問題を受けてAnthropicは2026年3月、Claude Codeに**マルチエージェント型Code Review機能**をリリースした。複数のAIレビューエージェントがPRを並行して検査し、バグの発見、誤検知の除去、重要度によるランク付けを行い、サマリーレビューとインラインコメントを投稿する仕組みだ。

導入後の成果は劇的だった。

- 実質的なレビューコメントが付くPRの割合：**16% → 54%**
- 1,000行超の大規模PRでの問題発見率：**84%**
- エンジニアが「誤検知」と判断した割合：**1%未満**

ここで重要なのは、「人がレビューしなくなった」のではなく、**「AIがレビューの一次スクリーニングを担い、人間がより重要な判断に集中できるようになった」**という構造変化だ。

## Stripeの「Minions」：週1,300PRの衝撃

Stripeの事例はさらに踏み込んでいる。社内で開発された**「Minions」**と呼ばれるAIコーディングエージェントは、毎週**1,300件以上のPR**をマージしている。これらのPRには人間が書いたコードは一行も含まれていない。

### Minionsの仕組み

エンジニアがSlackで絵文字リアクションをつけるだけでタスクがMinionsに割り当てられ、コーヒーを取りに行って戻ると5つのPRが準備されている——という運用だ。

技術的な核心は**[「Blueprint」アーキテクチャ](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2)**にある。Blueprintは2種類のノードを交互に組み合わせたステートマシンだ。

- **決定論的ノード（Deterministic Node）** — 固定的で予測可能な処理を行うステップ。同じ入力に対して常に同じ出力を返す。リンター実行、テスト実行、PR テンプレートへの整形など、AI の判断を一切介在させない純粋なロジック。
- **エージェントノード（Agentic Node）** — LLM が文脈を理解し、判断し、コードを生成するステップ。実装方針の決定、コード生成、リファクタリングの提案など、創造的な推論が必要な箇所に限定して投入される。

この2つを交互に配置することで、「AIがコードを生成 → 決定論的ノードがコンパイル・テストで検証 → 失敗すればAIに差し戻し」というフィードバックループが形成される。AIが毎回正しい必要はない。**システムが誤りを検知し、修正の機会を与える**構造になっている点が重要だ。CIが失敗した場合、エージェントにはもう1回だけリトライが許され、それでも失敗すれば人間にエスカレーションされる。

各Minionsは**隔離されたサンドボックス環境（Devbox）**で実行され、人間のエンジニアが普段使う開発環境と同じ基盤上で動く。

### しかし、人間はレビューしている

ここが議論の肝だ。**Stripeでは、Minionsが書いたコードを人間がレビューしている**。完全自動ではない。Stripe自身が「壁（guardrails）がモデルより重要」と明言しているように、AIの出力を制約する仕組みと人間の最終確認が信頼性の要となっている。

ただし、Minionsが得意とするのは設定変更、依存関係のアップグレード、軽微なリファクタリングといった**well-definedなタスク**だ。こうしたタスクのレビューは「コードの正しさ」の機械的な検証であり、設計判断を伴うレビューとは質的に異なる。

## 「人がコードレビューしない」の3つの解釈

この議論を整理すると、「人がコードレビューしない」には少なくとも3つの異なる意味がある。

### 1. 一次スクリーニングをAIが代替する

Anthropicのアプローチ。人間のレビュー負荷を下げ、見落としを防ぐためにAIが先にレビューする。人間は「AIが見つけた問題」と「AIが見落とした観点」に集中する。従来の「全行を目で追う」レビューから、**AIの出力をメタレビューする**形への移行だ。

### 2. 定型タスクのレビューを省略・簡略化する

Stripeのアプローチ。マイグレーション、依存更新、ボイラープレート生成など、パターンが明確なタスクでは、テストが通り、Blueprint内のバリデーションを通過すれば実質的にレビュー不要とする。**「レビュー不要の条件」を事前に定義する**リスクベースの考え方だ。

### 3. コードそのものを読まない

最も過激な解釈。コードの正しさはテスト・型検査・静的解析・AIレビューで担保し、人間は「要件を満たしているか」「設計方針に合っているか」だけを確認する。コードではなく**仕様と振る舞い**をレビューする世界だ。

## ハーネスエンジニアリング：レビュー不要の前提条件

「コードレビューしない」が成立するためには、レビュー以外の品質保証メカニズムが必要だ。ここで注目されているのが**ハーネスエンジニアリング**という概念である。

この用語を最初に提唱したのは、HashiCorp共同創業者でありGhosttyの作者としても知られる**Mitchell Hashimoto**だ。2026年2月5日に公開されたブログ記事[「My AI Adoption Journey」](https://mitchellh.com/writing/my-ai-adoption-journey)の中で、彼はAIエージェントと協働する中で確立した方法論として「Engineer the Harness」というステップを紹介した。エージェントがミスをするたびに、その特定のミスが**構造的に再発不可能**になるよう環境側を改修していく——この積み重ねが「ハーネスエンジニアリング」だ。彼が提示した公式は明快である：**Agent = Model + Harness**。この記事の公開から数週間のうちにOpenAIやAnthropicも関連するエンジニアリング記事を相次いで発表し、一気にバズワード化した。

「ハーネス」とは馬具のことで、優秀な馬（AIモデル）でも手綱がなければ制御できないという比喩だ。AIエージェントの出力品質は、モデルの性能よりも**それを動かす環境設計**に左右される。

具体的には以下の要素が含まれる。

- **タスク分解**：大きなタスクを、AIが確実にこなせる粒度に分割する
- **コンテキスト管理**：必要な情報だけをエージェントに渡す
- **出力バリデーション**：テスト実行、型チェック、リンターなどの自動検証
- **エスカレーションパス**：エージェントが判断に迷った場合に人間に戻す仕組み
- **Writer/Reviewerパターン**：あるエージェントが実装し、別のエージェントがレビューする

OpenAIのエンジニアリングチームが「人間はコードを1行も書かない」制約で5ヶ月間プロダクトを開発した実験では、100万行のコード、1,500件のPRが生成された。開発時間は手作業比で約1/10だったという。

つまり、**ハーネスが十分に成熟していれば、コードレビューという「人間による最終チェック」の必要性は確かに低下する**。

## 反論：「レビューしないと仕様に沿わない動作が出る」は本当か？

コードレビュー不要論に対する最も直感的な反論は、「人がレビューしなければ仕様に沿わない動作や予期せぬ動作が生まれる」というものだ。しかし、この主張はソフトウェア品質特性の観点から分解すると、実はコードレビューへの過大評価に基づいていることが見えてくる。

### ISO 25010が定義する品質特性とその検証手段

ソフトウェア品質の国際規格ISO 25010は、製品品質を8つの特性に分類している。「仕様に沿わない動作」「予期せぬ動作」がどの品質特性に該当し、それぞれに対してコードレビューがどの程度有効かを検証する。

| 品質特性 | 「仕様どおり動くか」との関連 | コードレビューの有効性 | より有効な検証手段 |
|---|---|---|---|
| **機能適合性** | 直接関連 | △ 低い | 自動テスト、E2Eテスト、受入テスト |
| **性能効率性** | 間接的 | × ほぼ無力 | 負荷テスト、プロファイリング |
| **互換性** | 間接的 | △ 低い | 結合テスト、契約テスト |
| **使用性** | 間接的 | × ほぼ無力 | ユーザーテスト、UIテスト |
| **信頼性** | 直接関連 | △ 低い | カオスエンジニアリング、フォールトインジェクション |
| **セキュリティ** | 間接的 | ○ 一定の有効性 | SAST/DAST、ペネトレーションテスト |
| **保守性** | 無関係 | ◎ 最も有効 | リンター、静的解析 |
| **移植性** | 無関係 | × ほぼ無力 | 環境別テスト |

### コードレビューが本当に得意なこと

この表から見えるのは、**コードレビューが「仕様どおりに動くか（機能適合性）」の検証に実はあまり向いていない**という事実だ。

Microsoft Researchの古典的な研究でも、コードレビューで発見されるバグの大半は「機能的な欠陥」ではなく「コードの明瞭性や保守性に関する指摘」であることが示されている。レビュアーがdiffを読んで「この条件分岐で入力Xのときに仕様と異なる動作をする」と見抜くのは、実はかなり難しい。特にコンテキストの全体像が見えない差分レビューでは、なおさらだ。

コードレビューが真に威力を発揮するのは**保守性**——命名の適切さ、抽象化の妥当性、コードの可読性——の領域であり、これはまさにAIレビューが急速に得意になりつつある領域でもある。

### 機能適合性は「動かして確かめる」が最強

「仕様に沿わない動作」を防ぐ最も確実な手段は、**コードを読むことではなく動かすこと**だ。

- **単体テスト** — 関数レベルの振る舞いを仕様として記述し、自動検証する
- **結合テスト・E2Eテスト** — システム全体の振る舞いが仕様に合致するかを検証する
- **契約テスト（Contract Test）** — サービス間のインターフェースが合意された仕様に準拠するかを検証する
- **受入テスト** — ビジネス要件レベルで期待される動作を検証する

これらはすべて**自動化可能**であり、コードレビューよりも再現性が高く、網羅性が高く、人間の注意力に依存しない。

Stripeの「Minions」がコードレビューの前にテストを自動実行するのはこのためだ。「テストが通っている」は「人間がコードを読んだ」よりも機能適合性の証拠として強い。

### 「予期せぬ動作」の正体

「予期せぬ動作」は、多くの場合以下のいずれかに起因する。

1. **仕様自体の曖昧さ・欠落** — テストが書かれていないエッジケース
2. **副作用** — 変更が他の機能に波及する
3. **環境依存** — 本番環境固有の条件で発生する

これらのうち、コードレビューで防げるのは主に（1）の一部だけだ。（2）はリグレッションテストの方が確実で、（3）に至ってはコードレビューでは原理的に検出できない。

むしろ、「人間がコードを読んでOKを出した」という事実が**偽の安心感**を生み、テストの不足を見過ごす原因になりうる。Anthropicの社内データで84%のPRが実質ノーレビューだったという事実は、**人間のレビューが品質保証として機能していなかった**ことの証左だ。

### コードレビューの「品質保証」は幻想に近い

まとめると、「コードレビューをやめたら品質が下がる」という主張が暗黙に前提としているのは次の仮定だ。

> 人間がコードを読めば仕様違反を見つけられる

しかし実際には、

- レビュアーは仕様の全体像を把握していないことが多い
- diffベースのレビューでは文脈が欠落する
- 注意力は有限であり、大きなPRほど見落とす
- 「Approve」がデフォルト化し、実質的な検証が行われていない

ソフトウェア品質特性の枠組みで見れば、コードレビューは8つの品質特性のうち**保守性**にのみ高い有効性を持ち、「仕様どおりに動くか」という機能適合性や信頼性の検証にはむしろ不向きだ。

**仕様適合の保証が目的なら、レビューではなくテストを書くべきだ。** そしてテストの生成と実行は、まさにAIエージェントが最も得意とする領域である。

## それでも人間がレビューすべきもの

では、AIに完全に任せてよいのか？ 答えはまだノーだろう。少なくとも現時点では、以下の領域では人間の判断が不可欠だ。

**設計判断** — このコードは問題を解決しているが、そもそも正しい問題を解いているのか。アーキテクチャの方向性は正しいのか。これはコードの「外側」の問題であり、AIがコンテキストを持ちにくい。

**暗黙知の伝達** — レビューはコードの品質保証だけでなく、チーム内の知識共有の機能も担っている。AIレビューはこの機能を持たない。

**セキュリティの最終防衛線** — AIが生成したコードにはAI特有の脆弱性パターンがある。AIがAIのコードをレビューする構造では、同じ盲点を共有するリスクがある。

**責任の所在** — コードに起因する障害が発生した場合、「AIがレビューしたので問題ない」は責任の回答にならない。組織として誰が品質に責任を持つのかという問題は技術では解決できない。

## 「レビューしない」のではなく「レビューの形が変わる」

結論として、「人がコードレビューしない」時代は来る。だがそれは「レビューが不要になる」という意味ではない。

**レビューの対象が「コード」から「仕組み」へとシフトする**のだ。

- コードの正しさ → テスト・型検査・AIレビューが担保
- 設計の正しさ → 人間が判断
- ハーネスの正しさ → 人間が設計・検証
- エージェントの振る舞い → 人間がモニタリング

Anthropicのデータが示すように、人間だけのレビューでは84%のPRが実質ノーレビューだった。AIレビューを導入して初めて、過半数のPRに意味のあるフィードバックが付くようになった。

皮肉なことに、**「人がレビューしない」仕組みを導入することで、コード品質に対するレビューの実効性はむしろ上がった**のだ。

議論すべきは「レビューするかしないか」の二項対立ではなく、**「何を人間が見て、何をAIに任せ、どう組み合わせるか」**の設計だ。そしてその設計こそが、ハーネスエンジニアリングの本質にほかならない。
