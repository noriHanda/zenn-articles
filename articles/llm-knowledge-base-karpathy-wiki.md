社内ドキュメントをベクトルDBに入れてRAGを組んだのに、まともな回答が返ってこない。そんな経験をしたことがある人は少なくないだろう。自分もそうだった。

原因は大抵、入れるドキュメントの選び方ではなく、入れ方にある。

Andrej Karpathyが提唱している考え方にLLM Wikiというものがある。LLMが参照するドキュメントは、人間が読むために書かれたドキュメントとは根本的に違う、という主張だ。

人間向けのドキュメントは前から順に読む想定で書かれている。「前章で述べた通り」「上記の要件に基づき」といった表現が当たり前に出てくる。読み手が文脈を持っている前提だからだ。

LLMはそうではない。ドキュメントをチャンクという断片に分割して処理する。前後のつながりは基本的に失われる。だから、どのチャンクを単独で取り出しても意味が通じるように書かれていなければ、検索で正しい断片を拾えても回答の精度は上がらない。

これがLLM Wikiの核にある考え方だ。

「ただ突っ込むだけ」がうまくいかない理由を、よくある失敗パターンで見てみる。

長いドキュメントをそのまま投入するケース。たとえばこんなチャンクが生まれる。

```
第3章 システム設計
3.1 概要
本システムは前章で述べた要件に基づき...
```

「前章で述べた要件」が何なのか、このチャンクだけではわからない。文脈依存の表現がそのまま残っている。

逆に分割しすぎるケースもある。

```
- 認証にはJWTを使用する
```

これだけ取り出しても、何のシステムの、どのエンドポイントの認証なのかが消えている。

もうひとつ厄介なのが、同じ概念が複数のドキュメントに散らばっているパターンだ。デプロイ手順が5つのファイルに分散していて、どれが最新かわからないままベクトルDBに入っている。LLMが矛盾した情報を拾ってくる原因になる。

こうした失敗を踏まえて、実践の中でたどり着いた設計の原則が3つある。

ひとつ目は自己完結性。すべてのチャンクは、それだけ読んでも意味が通じるように書く。

たとえば「前述の通り、この設定は本番環境では無効化する必要がある」では、何の設定の話なのか単体ではわからない。こう書き換える。

```
DEBUG_MODEフラグ（config/settings.py）は、本番環境では必ずFalseに設定する。
有効のままデプロイすると、スタックトレースが外部に露出するリスクがある。
```

ふたつ目は粒度の統一。1チャンクに1概念だけを入れる。ログイン処理の概要とパスワードリセットの仕様を同じチャンクに入れると、検索で片方を狙って引いたときにもう片方がノイズになる。目安は1チャンクあたり200〜400トークンくらいだ。

3つ目は文脈の明示。チャンクの冒頭に、何について、どのシステムの、いつ時点の情報かを書いておく。

```
[対象：受発注API v2] 認証仕様

このAPIはBearerトークン認証を使用する（2024年3月以降の仕様）。
トークンの有効期限は24時間。リフレッシュエンドポイントは /auth/refresh。
```

実践で一番効いたのは、この整理作業自体をLLMにやらせることだった。

Google Drive、Notion、Confluenceなどに散らばっている既存ドキュメントをLLMに渡して、ナレッジベース用に再構成させる。プロンプトはこんな形になる。

```
以下のドキュメントを、LLMが検索・参照しやすいナレッジベース用に再構成してください。

条件：
- 各チャンクは200〜400トークン程度
- 各チャンクは文脈なしで単独で意味が通じること
- 固有名詞・システム名・バージョン情報は省略しない
- 同じ概念を複数チャンクに重複させない
- 各チャンクの冒頭に [対象：XXX] 形式のラベルをつける

ドキュメント：
{document}
```

人手でやるより速いし、品質も安定する。

ある会社のGoogle Driveで実際に試した。対象はよくある「散らかったDrive」そのものだった。フォルダ構造は一応あるが形骸化していて、同じ内容のファイルが複数バージョン存在する。議事録と仕様書と手順書とメモが混在し、命名規則もないから開かないと中身がわからない。更新されないまま放置された古いドキュメントも大量にある。多くの会社で見覚えがある光景だと思う。

結果として、初回の整理だけでGoogle AgentSpace相当の検索精度が出た。RAGのヒット率は、そのまま突っ込んでいたときと比べて体感で大きく上がった。エンジニアが「あのドキュメントどこだっけ」と聞く場面もなくなった。エンタープライズ向けのSaaSを導入するより安く、自社の事情に合った形で実現できている。

よくある誤解にも触れておく。

ChromaDBやPineconeを使えば解決するという期待があるが、ベクトルDBはストレージにすぎない。何を入れるかがすべてで、良いDBに雑なチャンクを入れても精度は出ない。

ドキュメントが多いほど良いという思い込みもある。むしろ古い情報、重複、矛盾が精度を下げる。整理して不要なものを削ることこそが精度向上の本丸だ。

一度作れば終わりというわけでもない。ドキュメントが更新されるたびに対応するチャンクも更新する仕組みがいる。ナレッジベースは運用し続けるものだ。

LLM Wikiの考え方を一言にすると、LLMのために書き、LLMのために整理する、ということに尽きる。既存ドキュメントをそのまま流し込むのではなく、LLMが扱いやすい粒度と構造と文脈に変換する。その変換作業自体にLLMを使う。RAGの精度改善に限らず、AIエージェントの設計や社内へのAI導入にも通じる考え方だと思う。
