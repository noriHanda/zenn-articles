[健適文化](https://kenteki.org)という会社をやっています。AIエージェントを開発プロセスに組み込むための環境構築──ハーネスの設計、CLAUDE.mdの整備、テスト自動化の導入──を企業向けにお手伝いしています。

その仕事をしていると、AIを使う人が大きく二つのタイプに分かれることに気づきます。**バイブコーダー**と**ハーネスエンジニア**です。同じツールを使っているのに、片方はチームに負債を撒き散らし、もう片方は組織の生産性を底上げする。この記事は、その違いがどこから生まれるのかを言語化する試みです。

## バイブコーダーとは何者か

「バイブコーディング（vibe coding）」という言葉は、もともとAndrej Karpathy氏が2025年初頭に使ったのが広まったものです。コードを一行一行吟味するのではなく、AIに雰囲気（vibe）で指示を出し、出てきたものをそのまま受け入れて進めていくスタイルを指します。

個人のプロトタイプや週末のハッカソンなら、これは最高に楽しい。動くものが一瞬でできあがる魔法のような体験です。問題は、これを**チーム開発の本番コードで、無自覚にやり続ける人**が現れたときに起きます。

私はこのタイプの人を、敬意を込めず正確に「バイブコーダー」と呼びます。彼らの行動パターンはだいたい共通しています。

### バイブコーダーがやっていること

**負債を作り、また負債を作る。** AIが出したコードの中身を読まないので、何が起きているのか本人も把握していません。テストもない、設計の一貫性もない、既存のアーキテクチャを無視した実装が次々とマージされていきます。動いているように見えるのでPRは通る。けれど一ヶ月後、誰もそのコードに触れなくなります。

**他人にケツを拭かせる。** バイブコーダーが書いた（正確にはAIに書かせて中身を確認していない）コードがバグを出すと、デバッグするのは別の誰かです。本人は「AIが書いたから」と言って、コードの意図を説明できません。レビュアーは仕様書もコメントもないコードを前に、ゼロから読み解く羽目になります。生産したのは一人、後始末をするのは複数人。これが常態化します。

**スケジュールを不安定にする。** 一番厄介なのがこれです。バイブコーダーの見積もりは当てになりません。「AIですぐできます」が口癖で、実際デモまでは速い。けれど本番投入の段になって、エッジケース、認証まわり、既存システムとの整合性で一気に詰まる。「あと少し」が何週間も続き、チーム全体の計画が崩れます。**速いように見えて、予測可能性を破壊している**のです。

**鼻つまみにされる。** こうして、最初は「AIを使いこなす人」と見られていたバイブコーダーは、やがてチームの厄介者になります。彼のPRには警戒のまなざしが向き、彼の見積もりは割り引いて聞かれ、彼が触ったモジュールは他のメンバーが見て見ぬふりをする。本人に悪気はないことが多いのが、なお悲しいところです。

### 新しいモデルが出るたびに驚いている

バイブコーダーの典型的な症状をもう一つ挙げます。**新しいモデルが出るたびに、毎回ゼロから驚いている**ことです。

「Claudeの新バージョンすごい」「今度のはもっと賢い」と、リリースのたびにベンチマークを眺め、SNSで騒ぎ、自分のプロンプトを少し書き換えて「やっぱり賢くなった」と感心する。それ自体は悪くありません。問題は、**それ以上のことを何も積み上げていない**ことです。

モデルが新しくなっても、彼の開発フローは変わりません。相変わらずチャット欄に雰囲気で指示を投げ、出てきたものをコピペし、動かなければまた雰囲気で指示し直す。モデルの賢さが上がれば成功率は少し上がりますが、やっていることの構造は去年と同じです。モデルの進化に乗っているのではなく、モデルの進化に**振り回されている**。

この状態がなぜまずいか。モデルは商品であり、誰でも同じものを使えます。新モデルが出れば、世界中のバイブコーダーが一斉に同じ恩恵を受け、同じように驚きます。そこに差別化はありません。驚いているだけの人は、ツールの消費者であって、ツールを使った価値の生産者になれていないのです。

## ハーネスエンジニアとは何者か

同じAIを使う者として似た部類に捉えられがちですが、実はバイブコーダーと対極にいるのがハーネスエンジニアです。ハーネス（harness）とは、馬具──馬を御するための手綱や引き具のことです。AIモデルという力のある馬を、暴走させずに目的地まで走らせるための装具一式を指します。

ハーネスエンジニアは、AIに「いいコードを書かせる」ことを目的にしていません。**AIがいいコードを書かざるを得ない環境を設計する**ことを仕事にしています。この差は決定的です。

### Context Engineeringで業務フローを設計する

その中核にあるのがコンテキストエンジニアリング（context engineering）です。プロンプトを上手に書く「プロンプトエンジニアリング」の一歩先で、AIが判断を下すために必要な文脈──仕様、制約、コードベースの規約、テスト、検証ループ──を、どう構造化してAIに与えるかを設計する営みです。

具体的には、こういうものを整えます。

- **CLAUDE.md / ルールファイル**: プロジェクトの規約、ディレクトリ構造、命名規則、やってはいけないことを明文化し、AIが毎回参照できるようにする。バイブコーダーが毎回チャットで口頭説明している内容を、再利用可能な資産にする。
- **仕様の構造化**: 実装前にAIに質問させて仕様書（SPEC）を生成し、合意の取れた仕様を起点に実装させる。雰囲気ではなく文書で握る。
- **検証ループ（ハーネスの本体）**: リンター、型チェック、テスト、CIを、AIが自分で回せるように整える。AIがコードを書く → 決定論的な検証が誤りを拾う → AIに差し戻す、というループを作る。AIが毎回正しい必要はなく、**システムが誤りを捕まえて修正の機会を与える**構造にする。
- **人間が読むべきものの抽出**: AIが仕様の外で独自に判断した箇所をレポートとして出力させ、人間はコード全体ではなくその判断だけをレビューする。

これは個人のテクニックではなく、**業務フローそのものの再設計**です。だからハーネスエンジニアの成果は、本人がいなくなっても残ります。整えたハーネスの上では、チームの他のメンバーも、なんなら新人も、AIを使って一定品質のアウトプットを出せるようになる。バイブコーダーが属人的な負債を生むのと、ちょうど裏返しです。

### AIのROIを最大化する

経営の視点で見ると、この違いはROI（投資対効果）の差として現れます。

AIツールにはお金がかかります。トークン課金もライセンス費もかかる。バイブコーダーの使い方では、その投資が**負債の生産速度**に変換されてしまい、後始末のコストを差し引くと、しばしばマイナスになります。速くゴミを作って、それを片付けるのに人手がかかるなら、AIを入れない方がマシだった、という結論すらありえます。これが「AIを入れたけど効果が出ない」という現場で実際に起きていることです。

ハーネスエンジニアは逆です。検証ループが品質を担保するので、AIの出力量がそのまま価値に近づきます。出力を増やしても後始末のコストが比例して増えない。だからスケールする。AnthropicやStripeのような会社が、AIエージェントで週に1,000件単位のPRをマージできているのは、彼らがハーネスの設計に投資しているからです。モデルが賢いからではなく、**賢いモデルを安全に走らせる馬具を作ったから**です。

### 新しいモデルが出ても、驚かない

ハーネスエンジニアは、新モデルのリリースで右往左往しません。なぜなら、彼が設計したのは特定のモデルに依存したプロンプトではなく、**どんな馬が来ても御せる手綱**だからです。

新しいモデルが出たら、ハーネスエンジニアは粛々とそれを既存のハーネスに繋ぎ、検証ループを通し、ベンチマークではなく自分たちの実タスクで性能を測ります。モデルが賢くなれば、検証ループの差し戻し回数が減り、自律的に完了できるタスクの範囲が広がる。その恩恵を、感心ではなく**生産性の数字**として受け取ります。

目指しているのは、人間が一手ずつ指示する状態からの卒業です。仕様を渡せばAIが自分で実装し、自分でテストを書き、自分で検証ループを回し、詰まったところだけ人間に上げてくる。**AIが自律的に動くように業務を設計する**こと。新モデルはその自律の半径を広げてくれる存在であって、毎回驚く対象ではありません。驚きはセットアップが終わっていない証拠です。

## 二人の違いを一枚で

|  | バイブコーダー | ハーネスエンジニア |
|---|---|---|
| 設計対象 | プロンプト（その場限り） | 業務フローと検証ループ（再利用可能） |
| AIへの向き合い方 | 雰囲気で指示し、出力を信じる | 環境を整え、出力を検証する |
| 生み出すもの | 技術的負債 | 予測可能な生産性 |
| 後始末 | 他人にやらせる | システムが拾う |
| スケジュール | 不安定にする | 予測可能にする |
| 新モデルが出たとき | 毎回驚く | ハーネスに繋いで性能を測る |
| 組織での扱い | 鼻つまみ者 | 生産性の源泉 |
| AIのROI | しばしばマイナス | 最大化される |

## まとめ──バイブコーダーに悩まされても、AIを見捨てるな

ここまで読んで、「うちにもバイブコーダーがいる、もうAIなんてこりごりだ」と思った方がいるかもしれません。でも、それは結論を急ぎすぎです。

問題はAIではありません。**AIを馬具なしで走らせていること**です。手綱のない馬が暴走するのは馬のせいではなく、手綱を用意しなかった御者の問題です。バイブコーダーに悩まされているからといってAIを見捨てるのは、暴れ馬を一頭見ただけで「馬は使い物にならない」と結論するようなものです。

ハーネスエンジニアリングに至れば、景色は一変します。**圧倒的な生産性**──AIが自律的にタスクをこなし、人間は設計と判断に集中できる。そして**予測可能性**──検証ループが品質を担保するから、見積もりが当たり、スケジュールが崩れない。速さと安定の両方が手に入ります。バイブコーダーが速さと引き換えに安定を差し出していたのとは、まったく違う取引です。

そして、もしあなたが今、バイブコーディングをして新しいモデルが出るたびに驚いているのなら、それは次のステージへの招待状だと思ってください。驚くのをやめて、**AIが自律的に動くように設計する側**に回る。手綱を握る側、御者の側に立つ。そこに立てたとき初めて、新モデルは「すごいおもちゃ」ではなく「自律の半径を広げてくれる相棒」になります。

馬を見捨てる必要はありません。手綱を仕立てればいいのです。
